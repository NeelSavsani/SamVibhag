### Embedded group objects

`expenses` is a list inside `groups/{groupId}`, not an observed top-level collection. Expense maps contain `id`, `title`, numeric `amount`, `paidBy` (display name), `splitBetween` (display-name list), `date` (ISO-8601 string from model serialization), `category`, `splitType` (`equal`/`custom` in model comments), and `customSplits` (display-name to numeric amount map). IDs are generated from title/date by default, with existing records able to carry their own IDs. Expense add/edit replaces the full array; delete also replaces the full array.

`recordedSettlements` is likewise embedded in the group document. Maps contain `id`, `fromUser`, `toUser`, numeric `amount`, Boolean `isSettled`, and optional `settledAt` (ISO-8601 string). Legacy parsing accepts `from`/`to` aliases. Pending settlements are computed from expenses and recorded settlements in `GroupModel`; the current callable recomputes pending values server-side. `settlement_model.dart`, `group_model.dart`, and `functions/index.js`.

### Field and relationship uncertainties

- `members`, `memberUids`, `memberEmails`, and `memberUsernames` are independent arrays populated conditionally; index alignment is not guaranteed. Offline members have no UID. Current group creation/add-member code writes `memberIdentities` for registered members; legacy groups may lack it. Any data mapping must not infer identity from display name alone.
- Expenses and settlements identify parties by display name, not stable UID. `memberIdentities` currently maps group member display names to UIDs but may be absent, ambiguous, or stale in legacy data.
- Expense and activity timestamps have mixed representations in local code: group `createdAt` may be Firestore Timestamp or ISO string; expense dates are serialized ISO strings; activity timestamps are Firestore Timestamps, with parser support for DateTime/string too; settlement `settledAt` is ISO string. Production variants need inspection.
- `avatarPath` can be a local path or a Cloudinary URL. `group_info_screen.dart` uploads local group images to Cloudinary. No application use of `FirebaseStorage` APIs was found, despite the package being declared.
- `assets/service_account.json` is declared as a Flutter asset and read by `fcm_sender_service.dart` to make FCM HTTP v1 calls directly from the client. The file was not opened or copied. This is a significant credential-exposure/security concern to review separately; it is not needed to infer the Firestore schema.

## Database operations and query behavior found

- Groups: current user query uses Firestore `Filter.or` between `memberUids arrayContains uid` and `createdBy == uid`, then listens to snapshots and sorts client-side by `createdAt` descending (ID tie-break / null timestamps last). A similar OR query feeds Activity screen. Details can subscribe to one group document. Home includes a direct group document delete path; it does not cascade activity records and conflicts with current local Firestore rules (`allow delete: if false`).
- Users: point reads by UID, streams by UID, search query by exact `email` or `usernameSearch` with `limit(1)`, and one `whereIn` document-ID query for group invite tokens. `syncExistingUsersToUsernames()` performs a full users collection read with per-user reads/transactions; this is not visibly called from the current UI path in inspected code.
- Usernames: point reads by username document ID and fallback exact query on `users.usernameSearch`, limit 1.
- Activity: fetches all activity docs for a group during historical backfill; writes up to three deterministic historical events per group in a Firestore batch; live activity query orders by timestamp descending. There is no pagination in this code.
- Mutations: user-name claim/change and auth username repair use Firestore transactions. Group expense edits/deletes replace embedded arrays. Activity historical backfill uses batch writes. Member addition, group edits, group creation, and token updates use document writes/updates. Settlement, member addition, legacy identity migration, and group deletion also use callable Cloud Functions through direct HTTP requests with Firebase ID tokens.
- No `collectionGroup`, explicit cursors/pagination, or named composite-index configuration was found in the repository. Live Console indexes remain unknown.

## Authentication, authorization, and other Firebase services

- Firebase Authentication is initialized separately and remains necessary. Local code supports email/password and Google sign-in (web popup; native Google credential), password reset, email verification in registration flow, and sign-out. UID is read from `FirebaseAuth.currentUser` / `User.uid` and used for user document IDs, group creator/member IDs, and activity actor IDs. The list of enabled providers in production Console is unknown.
- The only local Firestore rules file is `firestore.rules` (and `firebase.json` points to it). It allows group reads/updates to group members/creator, constrains creator UID, restricts client edits to `memberIdentities` to creator, blocks direct `recordedSettlements` changes, disallows direct group delete, and allows activity read/create to parent group members. There are no local `users` or `usernames` matches; unmatched paths are denied by these local rules. The currently deployed rules cannot be determined without Console access.
- `functions/index.js` has an `onWrite` group trigger that compares member UIDs and sends FCM invitations, plus callable endpoints `addGroupMember`, `migrateGroupMemberIdentities`, `manageSettlement`, and `deleteGroup`. The trigger and callables use Admin Firestore. The delete callable uses recursive deletion for the group and descendants. These endpoints are part of the previous local implementation; deployed functions state/version is unknown.
- `firebase.json` configures Firestore rules and Functions only; no Realtime Database rules or database URL is configured. No `firebase_database` dependency/import or RTDB API use was found. This does not establish whether an RTDB instance exists remotely.
- Firebase Messaging and local notifications are used. FCM tokens live in `users/{uid}` and are consumed by Functions/client sender. Hive is initialized for the `samvibhag_storage` box and used for the dark-mode setting; no expense/group cache use was found. Cloudinary is used for group image upload. Firebase Storage dependency is present, but application API usage was not found.
- No scheduler or scheduled task was found in the local Functions source/package. Production scheduled functions cannot be ruled out without Console inspection.

## Migration risks and unresolved questions

1. Live counts, actual field variants, existing RTDB contents, deployed rules/functions, and production data cannot be verified until read-only Console access is available.
2. Group data is denormalized in one document with embedded expense/settlement arrays; replacing an entire array on edit/delete can race concurrent writes. Activity is separately stored and may not be atomically consistent with a group mutation.
3. Multiple models parse timestamps differently and stored timestamp types are mixed. Any future migration mapping will need a type-preserving policy, and a source scan alone cannot enumerate all live variants.
4. Name-based expense/settlement references and parallel membership arrays are ambiguous for duplicate names, offline members, or array drift. Stable UID mappings exist only in some records; the prior callable migration refuses ambiguous backfill.
5. Group/member authorization is currently expressed partly by local Firestore rules and partly by trusted callables; the users/usernames rules are absent locally. Deployed authorization must be inspected before deriving replacement rules.
6. Current home group deletion bypasses the callable, attempts direct delete, and does not remove activity docs. Local Firestore rules deny direct deletes. This is a code-path inconsistency; do not use it as a migration cleanup operation.
7. Client-included service-account asset is a credential/security concern. Preserve it and do not expose its contents during this audit; the deployment/app packaging arrangement needs a separate safe review.
8. Cloudinary URLs/local avatar paths, push tokens, profile PII, and duplicate user/profile fields require explicit treatment and access rules before a destination mapping can be approved.
