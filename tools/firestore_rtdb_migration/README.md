# Local Firestore → RTDB migration prototype

The migration CLI remains **synthetic-fixture-only**. A separate guarded `inventory_runner.mjs` uses the existing read-only adapters and the installed `firebase-admin` package for an explicitly invoked read-only inventory. It does not contain data-write, delete, migration, or deploy operations. It has not been run against live Firebase. The fixture contains invented IDs, `.invalid` emails, no real user data, and no credentials.

## Run

From the repository root:

```powershell
node tools/firestore_rtdb_migration/migrate.mjs
```

This is read-only and dry-run by default. It prints a source hash, planned destination hash, source/destination record counts, and number of deterministic output paths. The only fixture accepted by the CLI must be under this tool's `fixtures` directory.

The optional `--apply-local` mode writes a resumable JSON state file only under `tools/firestore_rtdb_migration/output/`. It does not connect to a Firebase service. It refuses to replace a conflicting value in a run namespace and keeps unrelated JSON tree values. It exists to exercise retries and local persistence; it is not a production migration mode.

Tests:

```powershell
node --test tools/firestore_rtdb_migration/test/migrate.test.mjs tools/firestore_rtdb_migration/test/inventory_memory.test.mjs tools/firestore_rtdb_migration/test/export_contract.test.mjs
```

## Synthetic Firestore JSON export contract

`json_export.mjs` defines `samvibhag-firestore-json-export-v1` and a local artifact publisher for the allowlisted synthetic fixture files only. It has no Firebase SDK, ADC, credentials, database client, or network path. It is not a live exporter and does not alter the migration planner or select an RTDB layout.

The source export keeps each Firestore document ID separate from its data, preserves group activity subcollections and nested JSON, and distinguishes absent fields from explicit `null`. A strict type-manifest array represents Firestore-range Timestamp seconds/nanoseconds, signed 64-bit Integer decimal strings, and Double IEEE-754 bit patterns through `null` placeholders. Duplicate, malformed, orphan, or mismatched descriptors fail validation. JSON numbers without an explicit captured type descriptor are rejected.

The installed local `@google-cloud/firestore` version is 7.11.6. Its documented public `useBigInt` setting makes `DocumentSnapshot.data()` return Firestore integers as `BigInt` and doubles as JavaScript `number`, preserving both type distinction and int64 precision without reading `_fieldsProto`. For a lossless adapter read, callers must set `preserveNumericTypes: true` and provide the expected SDK version; the adapter independently reads the installed package metadata, requires both versions to match 7.11.6, and applies `db.settings({useBigInt:true})` before the first query. Unknown versions or unavailable settings fail closed. Without this mode, decoded JavaScript numbers remain untyped and cannot be exported faithfully. Local tests use SDK-compatible fake `data()` values and verify ordering/configuration, but do not exercise real SDK snapshot decoding or establish production-data fidelity.

Type policy: Firestore strings, booleans, null, arrays, and maps use ordinary JSON when their nested values are supported. `Timestamp` is encoded as validated seconds plus nanoseconds. `BigInt` values produced by public `useBigInt` decoding are encoded as exact signed int64 decimal text; finite JavaScript numbers in that verified mode are doubles encoded as IEEE-754 binary64 bits, retaining integral-valued doubles and negative zero. `GeoPoint`, `DocumentReference`, `Bytes`/Blob, vector values, non-finite doubles, unknown SDK classes, cyclic values, and untyped numbers are rejected; no conversion is inferred for them. Unsupported values have no lossless representation in this contract yet.

The count manifest is recomputed from the export and separates Firestore documents (`users + usernames + groups + activities`) from embedded expenses and settlements. `exportStatus` and `serializationFidelityStatus` are separate from `projectionReadinessStatus`; a faithful export with ambiguous relationships may have blocked projection readiness, and an export never claims migration readiness. Unsupported Firestore SDK types fail closed.

Synthetic artifact publication stages the export and a pending marker in a temporary directory, validates the JSON round trip, then exclusively reserves the final directory and moves the prepared files into it. This reservation fails if any other process creates the destination after the initial existence check. It atomically renames `complete.json` into place as the final step. `readPublishedSyntheticExport(exportId)` is the shared reader: it accepts only a safe ID under the fixed synthetic output root, requires exactly `export.json` and `complete.json`, checks the marker version and SHA-256/byte length against the exact export bytes, then validates supported values, IDs, type descriptors, and recomputed counts before returning records. It emits only stable error codes. A failed attempt removes its unpublished output; an interruption can leave only a `.tmp-*` directory or a final directory without `complete.json`, both rejected by the reader. A marker is never written before source read, serialization, parse-back, manifest/count validation, and completion-manifest preparation have succeeded. Failure diagnostics distinguish blocked or unverified fidelity from a valid export that could not be published. The JSON export contains source values and is sensitive even when synthetic—never place real data in fixtures or output.

The schema proposal's top-level active collections and the planner's run-scoped `migrationRuns/{runId}/projected` layout remain competing options. The export contract is independent of either. No destination layout was selected or changed.

Milestone 7.0 records the non-production SDK test prerequisites, test matrix, source-consistency trade-offs, and pre-export operational gates in [the SDK and consistency preflight](../../docs/milestone-7-sdk-consistency-preflight.md). The Firebase CLI and emulator configuration are not currently available in this workspace, so actual SDK numeric decoding remains unverified; no emulator was started.

## Mapping decisions and corrections from Milestone 2 review

1. **No positional UID mapping.** The earlier proposal said equal-length unique `members[]` and `memberUids[]` might support a legacy backfill. That is unsafe: member arrays are appended independently for offline users and can drift while still having equal lengths. This utility never joins those arrays. Only explicit, well-formed, unique `memberIdentities` entries create name/UID links. A settlement payer with no explicit mapping is not authorized as a member; the group creator remains authorized by `createdBy`.
2. **Membership versus profile presence.** The synthetic preflight requires referenced group member/creator UIDs and username UIDs to have corresponding user profile documents in its fixture. A live migration must separately verify whether an Auth UID may legitimately lack a `users/{uid}` profile; if so, the policy needs an explicit review decision before changing this check. The utility never queries Firebase Auth.
3. **Expense splits.** Expense `paidBy`, `splitBetween`, and `customSplits` remain exactly as stored and display-name keyed. Custom split amounts are checked for finite numeric values, but the utility does not re-split, rebalance, sum-correct, or recompute business values. Ambiguous or unknown name references fail preflight rather than resolving to the first match. Dynamic map keys are encoded reversibly.
4. **Settlement semantics and legacy aliases.** In the current model, pending settlement `fromUser` is the balance debtor/responsible payer and `toUser` is creditor; it is not inferred from the expense author. If either canonical field is absent, the planner maps the corresponding legacy `from` or `to` string to it. If both forms exist, they must match exactly; malformed or conflicting aliases fail closed. The projection keeps original alias fields and adds canonical fields where needed; the source archive preserves the original record unchanged. Parties must still match exactly one group member name, so ambiguous relationships are never guessed. The synthetic checks validate IDs, parties, amount, status, and stable identity authorization; they do not reject historical amounts merely because current expenses might now yield a different balance. Recomputing balances during migration could alter or misclassify historical records.
5. **Dates and missing values.** The adapter's type manifest uses logical paths into group document data, including array indexes for embedded expense and settlement entries (for example `/groups/{groupId}/data/expenses/0/date`). Both the archive and each embedded projection consume these same source pointers. Timestamps preserve seconds/nanoseconds, explicit null is tagged because RTDB null removes a node, and absent fields remain absent. ISO strings remain strings. Integer/double descriptors are preserved in tagged numeric envelopes. Type descriptors that point to missing fixture data are fatal.
6. **IDs and duplicates.** Firestore document IDs for users, usernames, groups, activities are retained in the archive and encoded for RTDB paths. Embedded expense/settlement records require nonempty IDs. Duplicate source IDs, activity path collisions, or missing embedded IDs fail before writes. The local utility does not invent the runtime random UUID fallback used by `SettlementModel.fromMap` for legacy missing IDs.
7. **RTDB key encoding.** Safe ordinary keys remain unchanged; unsafe keys and every key beginning with reserved prefix `_k_` are encoded as `_k_` plus UTF-8 base64url. The reserved-prefix escape makes the mapping injective, including when an original key resembles an encoded key. Every map entry also stores its original key. Duplicate document IDs and projected path collisions are still checked.
8. **Archive and projection.** Each synthetic source document is represented in `sourceArchive`; active logical projections split embedded groups into metadata, ordered independent membership arrays, membership indexes, expense IDs, settlement IDs, and activity IDs. Group document archive content and activity archives have separate `document`/`activities` nodes to avoid writing both a value and children at the same RTDB path.
9. **Counts and verification.** Source counts distinguish Firestore documents from embedded expense/settlement records. Destination counts distinguish projection and archive records. Canonical SHA-256 hashes cover stable source content and each planned destination path/value. Verification checks missing, differing, and unexpected record paths.

## Local-only safety boundaries

- Migration planning and the CLI import only Node built-ins. The optional read-only adapter accepts already-initialized Firestore/RTDB clients by dependency injection and does not import Firebase SDKs itself.
- Default execution reads one synthetic JSON fixture and writes nothing.
- The planner accepts only the audited source collection set (`users`, `usernames`, and `groups`). An additional fixture collection fails with `unsupported_source_collections`; the planner never hashes an unprojected collection and then silently omits its records.
- `--apply-local` writes only to this directory's `output` folder. It has no remote mode or environment variable for Firebase endpoints.
- Fixture CLI errors emit only a stable diagnostic code. Dry-run and verification reports expose aggregate counts/status only; they omit source/destination paths, identifiers, names, hashes, and arbitrary map keys. The local state file created by the explicit `--apply-local` simulation still contains the synthetic fixture projection/archive and journal needed to exercise resumability; do not place real user data in fixtures or output.
- The fixture CLI loads no account credential, `.env`, service account, or production source file. The separate live inventory runner resolves ADC only after explicit inventory arguments and confirmations pass; credential metadata and tokens are never logged.
- `inventory_runner.mjs` is separate from the fixture CLI. It accepts only the `inventory` command, pins `samvibhag-a2299`, `https://samvibhag-a2299-default-rtdb.asia-southeast1.firebasedatabase.app`, and ADC principal `samvibhag-migration-inventory@samvibhag-a2299.iam.gserviceaccount.com`, requires operator confirmations, and prints aggregate structure only. `--expected-principal` is optional as an assertion and accepts only that exact pinned value; a conflicting value is rejected before ADC lookup or SDK initialization. Errors are logged by code only. `--page-size` may be set from 1 to 25 (default 1); `--max-records` may be lowered from 10,000 (default and hard maximum 10,000). Other limits are fixed or may only be lowered through the local adapter API; no option can raise a hard cap. The local principal comparison does not prove the account's actual IAM permissions or deployed RTDB rules.
- The report separates `inventoryStatus` from `migrationReadinessStatus`. `inventoryStatus: complete_for_configured_scope` is emitted only after successful evidence for all five configured RTDB paths; a root-only `/samvibhag/v1` result is rejected as malformed and cannot establish five-path completeness. It says nothing about migration readiness, the whole database, or point-in-time consistency. Unsupported Firestore values set readiness to `blocked_unsupported_source_values`; without such values readiness remains `not_assessed_by_inventory`, never migration-ready. Firestore scope is only `users`, `usernames`, `groups`, and each group's `activities` subcollection. Firestore reads stop at 10,000 document/activity records, 256 KiB estimated JSON per Firestore record, or 16 MiB total; these are hard caps. The values of embedded expenses and settlements are covered by the containing group-document byte limit. Firestore read/page/limit failures abort with a stable code and no partial source snapshot. An RTDB path failure is reported as `incomplete_for_configured_scope`, includes only fixed allowlisted path statuses, and exits nonzero.
- Tests import the runner but inject fake identity and SDK clients. They do not initialize Firebase or access the network.
- The RTDB adapter checks only these fixed, schema-derived collection paths: `/samvibhag/v1/users`, `/samvibhag/v1/usernames`, `/samvibhag/v1/groups`, `/samvibhag/v1/userGroups`, and `/samvibhag/v1/migrationRuns`. These five root children are described in the proposal, but production child structure and contents have not been verified. The inventory does not infer additional paths. It does not read `/`, `/samvibhag/v1` as a whole, or sibling roots. The planner's active projection/archive is currently run-scoped under `/samvibhag/v1/migrationRuns/{runId}`; the proposal also describes top-level active collections. That placement difference is unresolved and must be decided before migration. A present child is a potential conflict, never evidence that the namespace is empty or safe.
- Each fixed collection is paged by key with a default page size of 1; `--page-size` can raise it to at most 25. The default and hard maximum is 10,000 records overall; `--max-records` can lower that ceiling. Other hard stops are 256 KiB estimated JSON per record, 16 MiB estimated JSON across accepted records, and 256 MiB process RSS. Limits are checked while scanning; on any exceeded limit, invalid/duplicate key, unsupported value, or read error, the report becomes `incomplete_for_configured_scope`, reports only safe aggregate issue counts and the attempted fixed path/status, stops scanning, and the CLI exits nonzero. It never calls a whole-parent `.get()`.
- RTDB returns the full value of each selected child. Therefore the 256 KiB record check occurs immediately after that response is materialized and cannot prevent a single oversized child from briefly exceeding the process memory budget. RSS is measured after each page returns, so it likewise cannot cap a spike within an SDK request. These application limits bound continued processing, not the SDK's peak allocation. Do not run live inventory until a safe size estimate exists; for a strict memory guarantee, a separately reviewed isolated worker with an OS memory limit or a different reviewed record layout is required.
- Firestore query pages are capped at 200 and each page/document is checked before processing continues. The SDK may still materialize a full query page before per-document byte checks run; the limits do not provide a hard peak-memory guarantee for one unusually large page or document.
- Reports include structural counts and approximate JSON byte totals only. `complete_for_configured_scope` means all five configured child paths were paged successfully within limits. It does not establish completeness of unlisted descendants/children, the whole RTDB namespace/database, or a point-in-time consistent snapshot. Unknown root children are unchecked. Each successful path is marked present or absent; failures/limit stops are explicit, with later paths not claimed as checked.
- Its `databaseAuthVariableOverride` identifies RTDB reads as `samvibhag-migration-inventory-reader`; the deployed RTDB rules must already allow that identity to read `/samvibhag/v1` while denying its writes. The Admin SDK override can downscope RTDB access only when the *deployed* rules enforce it. The override does not reduce Firestore IAM privileges. Confirmation flags are operator attestations, not evidence. Verify the actual ADC principal's IAM and deployed rules for the exact instance independently before execution.
- Successful reports list the exact RTDB path checked and its status (`accessible_present` or `accessible_absent`). A failed path read aborts with an incomplete status, the fixed path, and a nonzero exit code. The report explicitly states that the whole database was not inventoried and that reads are not point-in-time consistent.
- The report emits collection counts, relationship/ID issue counts, settlement alias counts, unsupported type counts, and fixed RTDB path statuses. It does not include record IDs, profile fields, tokens, or RTDB values. It does not claim unchecked RTDB paths are absent or empty.
- Do not use the read-only inventory runner until the identity and permission checks below have been completed. It is not a migration or backup tool.

## Live inventory preflight — must be completed before use

1. Select the dedicated approved ADC service-account principal and verify its exact email independently in the Google Cloud IAM Console. The runner is pinned to `samvibhag-migration-inventory@samvibhag-a2299.iam.gserviceaccount.com`; `--expected-principal` can only repeat this value and cannot redefine trust. Do not paste credentials or tokens into a command, report, or chat.
2. Verify the credential project ID is exactly `samvibhag-a2299`. The runner checks both Google Auth's resolved project and the ADC credential metadata project ID, and aborts when either is missing or different.
3. In IAM, confirm the principal has only the Firestore read access required for listing and reading documents and no write/deploy permissions. `roles/datastore.viewer` is read-only but broader than document reading; prefer a reviewed custom role limited to required read permissions if available. The runner's `--confirm-firestore-read-only-iam-verified` is an operator attestation, not an IAM-policy inspection.
4. In Firebase Console, verify the exact RTDB instance URL and project ownership. The runner currently accepts only the pinned URL above; acknowledge it with `--confirm-database-url-verified`.
5. Inspect the currently deployed RTDB rules without editing them. Confirm the rules recognize the fixed override UID `samvibhag-migration-inventory-reader`, grant read access to `/samvibhag/v1`, and deny writes for that identity throughout the rule tree. Rules inheritance means a child denial cannot undo a parent grant. If current rules do not provide this read-only access, stop. Do not change rules as part of inventory.
6. Verify the above permissions for the actual principal and database before supplying `--confirm-rtdb-read-only-rules-verified`. A flag is an acknowledgment, not proof. If any check is uncertain, do not execute the runner.

The live runner was intentionally not invoked during local implementation. A successful live read is not yet verified, and no production connection has occurred. `/samvibhag/v1` was selected from the schema proposal; it is not presumed empty or safe. Any `accessible_present` result requires a separate reviewed conflict and retention decision before migration.

## Synthetic memory probe

`node --test tools/firestore_rtdb_migration/test/inventory_memory.test.mjs` generates invented collection records and feeds key pages through a fake client. It measures local process heap/RSS observations and the adapter's estimated JSON bytes; it makes no Firebase calls. The fake data itself is already resident in the test process, so this is a local processing probe, not an end-to-end peak-memory benchmark. It does **not** measure Firebase Admin SDK network transport, SDK deserialization, production data size, or peak memory for one oversized RTDB child. Obtain an authorized non-content size estimate before considering live access and retain substantial memory headroom.

## Emulator limitation

Firebase Emulator Suite is not available/configured in this environment: the Firebase CLI executable was not found, and repository `firebase.json` contains no `emulators` configuration. Therefore the tests below use only local fake stores and synthetic fixtures. Emulator-based Auth/Firestore/RTDB/Functions rule integration has not been run. The pure `canManageSettlement` helper is a local policy test, not a substitute for deployed/emulator security-rule tests.

## Remaining risks and live-console decisions

- Live Console facts remain unverified: project access, RTDB URL/region/existing content/rules, deployed Firestore rules/indexes, production schema/counts, functions/schedules, Auth providers, Storage contents, concurrent writers, and backup/retention constraints.
- The live adapter and inventory report have only been tested with fake SDK clients, not against Firestore or RTDB emulators. Firestore source results remain materialized in process memory. RTDB collection pages are bounded, but one selected RTDB child is fully materialized by the SDK before its per-record check.
- RTDB pagination depends on the deployed SDK supporting the tested `orderByKey`/`limitToFirst`/`startAfter` query semantics. This is only fake-client tested locally. The five configured collections omit any other namespace descendants; no whole-project/namespace completeness is claimed. The proposed schema versus planner destination placement also needs resolution before migration.
- No coherent source snapshot can be guaranteed while current Firestore writers are active. The current code has no durable change log or uniform version field. A future production process must use a verified write freeze or separately approved change-capture design.
- No emulator test validates RTDB Security Rules or Cloud Functions. Current Firestore authorization and group operations remain unchanged.
- The previous schema's creator index and source profile existence checks need live validation; do not promote staging data until its authorization projection has been reviewed against actual users and group records.
- Exact numeric type preservation from Firestore Admin SDK extraction requires the eventual source adapter to capture an explicit type manifest before JSON serialization. This fixture tool supports such a manifest but cannot itself prove a future export adapter retains integer/double distinctions.
- No app code, Firebase config, rules, functions, or production data was changed.
